# План проекта: стенд для KEM и блочных шифров

Oct 8, 2026 · @Alpharius

Делаем на C++20 универсальный стенд: любой KEM в паре с любым блочным шифром и режимом, а поверх — хранилище ключей, бенчмарки и анализ. Обязательная часть: ML-KEM и HQC, AES и «Кузнечик», собственные реализации, проверенные официальными тест-векторами.

## Цель и объём

Итог проекта — библиотека `pqlab` и три утилиты (`pqtool`, `pqbench`, `pqanalyze`), которые закрывают все четыре пункта задания для любой комбинации «KEM + блочный шифр + режим». Весь криптографический код пишем сами. OpenSSL и liboqs подключаем только в тестах и бенчмарках как эталон для сверки.

**Что входит в проект:**

- ML-KEM-512/768/1024 (FIPS 203) и HQC-1/3/5: KeyGen / Encaps / Decaps, совпадение с официальными KAT;
- SHA3-256/512, SHAKE128/256 — нужны обоим KEM;
- AES-128/256 и «Кузнечик» (ГОСТ Р 34.12-2015), режимы CTR и GCM;
- гибридное шифрование KEM-DEM для файлов;
- хранилище ключей: генерация, хранение под паролем, ротация;
- бенчмарки всех примитивов с графиками;
- лавинный эффект и одна атака на каждый KEM и на каждый блочный шифр;
- отчёт и презентация.

Зависимости идут только сверху вниз. Ни одно приложение не вызывает ML-KEM или AES напрямую, поэтому третий KEM или новый шифр сразу попадает в бенчмарки, анализ и хранилище. Режимы работают поверх любого `BlockCipher`, так что GCM с «Кузнечиком» получается бесплатно.

## Интерфейсы ядра

Интерфейсы фиксируем до написания алгоритмов. Тогда бенчмарки, хранилище и анализ пишутся параллельно на заглушках, а новый алгоритм подключается одной строкой в реестре.

```cpp
namespace pq {

using Bytes    = std::vector<uint8_t>;
using ByteView = std::span<const uint8_t>;
class SecureBytes;               // зануляет память в деструкторе

class Rng {                      // SystemRng (getrandom) | DeterministicRng (для KAT)
public:
  virtual void fill(std::span<uint8_t> out) = 0;
};

struct KemSizes { size_t pk, sk, ct, ss; };
struct KeyPair  { Bytes pk; SecureBytes sk; };
struct Encapsulation { Bytes ct; SecureBytes ss; };

class Kem {
public:
  virtual std::string_view name() const = 0;       // "ML-KEM-768", "HQC-1"
  virtual int security_level() const = 0;          // категория NIST 1/3/5
  virtual KemSizes sizes() const = 0;
  virtual KeyPair keygen(Rng&) const = 0;
  virtual Encapsulation encaps(ByteView pk, Rng&) const = 0;
  virtual SecureBytes decaps(ByteView sk, ByteView ct) const = 0;
};

class BlockCipher {
public:
  virtual std::string_view name() const = 0;       // "AES-256", "Kuznyechik"
  virtual size_t block_size() const = 0;
  virtual size_t key_size() const = 0;
  virtual void set_key(ByteView key) = 0;
  virtual void encrypt_block(const uint8_t* in, uint8_t* out) const = 0;
  virtual void decrypt_block(const uint8_t* in, uint8_t* out) const = 0;
  virtual int  rounds() const = 0;
  virtual void set_rounds(int r) = 0;              // урезанные раунды — только для анализа
};

class Aead {                                       // GCM поверх любого BlockCipher
public:
  virtual Bytes seal(ByteView key, ByteView nonce, ByteView aad, ByteView pt) = 0;
  virtual std::optional<Bytes> open(ByteView key, ByteView nonce, ByteView aad, ByteView ct) = 0;
};

class Registry {                                   // фабрика по имени
public:
  std::unique_ptr<Kem>         kem(std::string_view name);
  std::unique_ptr<BlockCipher> cipher(std::string_view name);
  std::unique_ptr<Aead>        aead(std::string_view mode, std::string_view cipher);
  std::vector<std::string>     list_kems(), list_ciphers(), list_modes();
};

} // namespace pq
```

Правила к интерфейсам:

- У каждого KEM есть ещё детерминированные варианты `keygen_derand(seed)` и `encaps_derand(pk, m)`. Они нужны для KAT и для лавинного теста (инверсия бита в seed или в m).
- Секреты живут только в `SecureBytes`. Сравнение секретов — только `ct_equal`, ветвления по секретам запрещены.
- Ошибки формата (неверная длина, проваленная проверка модуля в ML-KEM) бросают `pq::Error`. Отказ в Decaps ошибкой не считается: это неявный отказ, возвращается псевдослучайный K.

## Пункт 2: создание, хранение и смена ключей

Строим систему по схеме envelope encryption. Данные шифруются случайным ключом данных (DEK), а DEK упаковывается через KEM. Для смены ключа KEM тогда достаточно переупаковать заголовок файла, а сами данные не перешифровываются.

### Создание

- Источник энтропии — `getrandom()`. Для воспроизводимых тестов есть детерминированный DRBG на SHAKE256, в боевых режимах он запрещён.
- Секретный ключ храним как seed: 64 байта (d, z) для ML-KEM и seed для HQC. Полный ключ разворачиваем при загрузке. В отчёте сравниваем выигрыш в объёме и цену развёртки во времени.
- У каждого ключа есть идентификатор `key_id = SHA3-256(pk)[0..16]`. Он записывается в каждый конверт, чтобы годы спустя найти нужный ключ.

### Хранение

- Хранилище — каталог `~/.pqlab/keystore/`, один файл на ключ. Метаданные лежат в открытом JSON: алгоритм, `key_id`, дата создания, срок действия, статус, счётчик использований. Секрет хранится зашифрованным.
- Секрет шифруется так: пароль → PBKDF2-HMAC-SHA3-256 (≥ 600 000 итераций, случайная соль) → мастер-ключ → AES-256-GCM. Метаданные идут в AAD, поэтому подмена алгоритма или статуса ломает проверку тега.
- Секреты в памяти: `SecureBytes` с занулением, которое компилятор не выкинет, и `mlock`, чтобы страницы не уходили в swap. Права на файлы — `0600`.
- Журнал аудита пишется только добавлением: кто, когда и какую операцию выполнил. Записи сцеплены хешами, так что правка задним числом видна.

### Жизненный цикл и смена

Статусы ключа: `active` → `retired` → `destroyed`, плюс `revoked` из любого состояния. Ключ `active` шифрует и расшифровывает, `retired` только расшифровывает старое. При `destroyed` секрет стирается, метаданные остаются.

1. **Ротация по политике.** Поводом служит возраст ключа или число инкапсуляций. `pqtool rotate` создаёт новый `active`, а старый переводит в `retired`.
2. **Переупаковка (rewrap).** `pqtool rewrap` делает Decaps старым ключом, затем Encaps новым, перешифровывает 32-байтный DEK и перезаписывает только заголовок файла. После этого старый ключ можно уничтожить.
3. **Миграция алгоритма.** Тот же rewrap с ML-KEM на HQC или с 512 на 1024. Это демонстрирует криптогибкость — именно ради неё NIST выбрал запасной HQC.
4. **Смена мастер-пароля.** Перешифровать придётся все секреты хранилища, поэтому операция атомарная: всё пишется во временный каталог и подменяется через `rename`.

### Формат конверта

```text
часть A (не меняется):     magic "PQL1" | version | aead_id | data_nonce_prefix
часть B (меняется при rewrap): kem_id | key_id[16] | len(ct_kem) | ct_kem | wrap_nonce | wrapped_DEK[32] | wrap_tag
данные (не меняются):     chunk_0 | tag_0 | chunk_1 | tag_1 | ...
```

Данные шифруются случайным 32-байтным ключом данных (DEK) кусками по 64 КБ. Nonce куска состоит из `data_nonce_prefix`, номера куска и флага последнего куска, поэтому куски нельзя переставить или обрезать. AAD кусков — только часть A: тогда rewrap не ломает их теги.

DEK упаковывается через AEAD на ключе `KEK = HKDF(K, salt = ct_kem, info = "pqlab" ‖ kem_id ‖ aead_id)`, где K — общий секрет из Encaps. AAD упаковки — части A и B целиком. Rewrap переписывает только часть B: несколько килобайт независимо от размера файла.

### Сценарии для защиты

- [ ] Создать ключ, зашифровать файл, расшифровать его после перезапуска с паролем
- [ ] Ротация: старые файлы читаются, новые шифруются новым ключом
- [ ] Rewrap 1 ГБ файла за миллисекунды (переписывается только заголовок)
- [ ] Неверный пароль, подменённые метаданные или битовая ошибка в файле — отказ без утечки данных
- [ ] После `destroy` старые файлы, не прошедшие rewrap, становятся нечитаемыми (crypto-shredding)

## Пункт 3: оценка скорости

Один движок `pqbench` меряет любой примитив из реестра и пишет CSV. Python-скрипты в `scripts/` строят по нему все графики для отчёта. Каждое число в отчёте должно воспроизводиться одной командой.

### Что меряем

| Объект | Метрики | Разрезы |
| --- | --- | --- |
| KEM | Такты и микросекунды на KeyGen, Encaps, Decaps; операций в секунду; размеры pk, sk, ct; пиковая память и стек | Все наборы параметров; наша реализация против liboqs (ref и AVX2) и OpenSSL 3.5+ |
| Блочные шифры | Такты на байт, МБ/с, стоимость расписания ключа | Наша реализация против OpenSSL |
| Режимы | МБ/с на сообщениях от 16 Б до 64 МБ | ECB, CBC, CTR, GCM × каждый шифр |
| KEM-DEM целиком | Время шифрования файла; точка, с которой симметричная часть перевешивает KEM | Матрица KEM × AEAD × размер файла |
| Хранилище | Время разблокировки (PBKDF2), rewrap против полного перешифрования | Число итераций, размер файла |
| Компиляция | Влияние флагов на скорость | GCC и Clang; `-O0`, `-O2`, `-O3`, `-march=native` |

### Как меряем

- Сначала прогрев, потом ≥ 10 000 итераций для KEM и ≥ 1 с непрерывной работы для шифров. В отчёт идут медиана, перцентили p5/p95 и стандартное отклонение, а не только среднее.
- Время снимается двумя способами: `std::chrono::steady_clock` даёт наносекунды, `rdtsc` с `lfence` — такты. Для сравнения реализаций основная единица — такты.
- Шум убираем так: выключаем turbo boost, ставим governor `performance`, привязываем процесс к ядру через `taskset`. Результат надо защитить от оптимизатора, иначе вычисление вырежется (аналог `DoNotOptimize`).
- В каждый CSV вместе с результатами записываются модель CPU, компилятор, флаги и хеш коммита. Итоговые числа снимаем на одной машине.
- Профилируем через `perf record` или flamegraph. В отчёте показываем, где тратится время: NTT и сэмплинг в ML-KEM, умножение и декодер в HQC, Keccak в обоих.

### Графики для отчёта

1. Столбцы по группам: KeyGen, Encaps и Decaps для шести наборов параметров, логарифмическая шкала тактов.
2. Размер данных на проводе (pk + ct) против тактов на рукопожатие: точка на каждый набор параметров KEM.
3. Пропускная способность режимов в зависимости от размера сообщения: линия на каждую пару «шифр + режим».
4. Доля KEM в общем времени KEM-DEM в зависимости от размера файла.
5. Ускорение от оптимизаций: наивная версия → оптимизированная (NTT, Карацуба), столбцы для каждого примитива.

## Пункт 4: лавинный эффект и атаки

Утилита `pqanalyze` считает лавинный эффект для любой функции «байты → байты», так что один движок обслуживает и шифры, и KEM. На каждый примитив делаем одну основную атаку с рабочим кодом и числами и оцениваем её применимость к полной версии.

### Лавинный эффект: блочные шифры

- **Лавина по открытому тексту и по ключу.** Инвертируем один бит, считаем расстояние Хэмминга между шифротекстами, берём ≥ 10⁵ случайных пар. Для 128-битного блока ожидаем среднее 64 бита и стандартное отклонение ≈ 5.66. Распределение сравниваем с Binomial(128, ½) критерием χ².
- **SAC (строгий лавинный критерий).** Строим матрицу 128 × 128: вероятность того, что входной бит i меняет выходной бит j. Рисуем тепловую карту и считаем максимальное отклонение от ½.
- **BIC (независимость битов).** Проверяем, что пары выходных битов меняются независимо: считаем корреляцию.
- **По раундам.** Через `set_rounds(r)` строим кривую «число изменившихся битов от числа раундов» для AES и «Кузнечика». Это главный график раздела. AES должен выйти на полную диффузию к 2-му раунду. У «Кузнечика» преобразование L — MDS-матрица на 16 байтах, поэтому ожидаем ещё быстрее.
- **Режимы.** Смотрим, как распространяется изменение бита в блоке i открытого текста и в блоке i шифротекста:
  - ECB — изменяется только блок i;
  - CBC — при шифровании меняются все блоки после i, при расшифровании разрушается блок i и один бит в i+1;
  - CTR — меняется ровно один бит, лавины нет;
  - GCM — подделка отвергается по тегу.
- **Статистические тесты.** На потоке CTR прогоняем подмножество NIST SP 800-22: frequency, block frequency, runs, longest run, serial.

### Лавинный эффект: KEM

У KEM нет одного входа и выхода, поэтому мерим несколько путей через детерминированные API:

| Инверсия бита в… | Смотрим на… | Ожидание |
| --- | --- | --- |
| seed в KeyGen | pk, sk | ≈ 50% бит: всё получается из SHAKE |
| m в Encaps | ct и K | ≈ 50%: r и K выводятся через G(m ‖ H(pk)) |
| m во внутреннем PKE при фиксированном r | ct | **Лавины нет**: меняется один коэффициент v или один блок кода |
| ct в Decaps | K | ≈ 50%: срабатывает неявный отказ, K = J(z ‖ ct) |
| pk в Encaps | K | ≈ 50%: H(pk) входит в G |

Третья строка — главный вывод раздела. Лавинный эффект даёт не сама решётка или код, а хеширование в FO-преобразовании. Это стоит показать на защите.

| --- | --- | --- | --- | --- |
| ML-KEM | Оракул проверки открытого текста на K-PKE без FO | Полное восстановление s специально построенными шифротекстами, порядка тысяч запросов; считаем число запросов для 512/768/1024 | С FO и неявным отказом оракул исчезает — атака неприменима. Показывает, зачем нужен FO | 1 |
| ML-KEM | Timing-утечка в духе KyberSlash | Вариант с делением `/ q` в Compress против нашего варианта с постоянным временем; t-тест по времени выполнения находит утечку в первом | Применима к неаккуратным реализациям, не к алгоритму | 1 |
| HQC | ISD: Прейндж, Ли–Брикелл, Штерн | Восстановление (x, y) из (h, s) при n ≈ 50–300; график времени от n и w | Экстраполяция на HQC-1 даёт ≥ 2¹²⁸ операций — неприменима. Сравниваем с оценками авторов | 2 |
| HQC | Timing сэмплера фиксированного веса | Сэмплер с отбраковкой против сэмплера с постоянным временем, измерение утечки | Реальная историческая уязвимость ранних версий HQC | 2 |
| AES | Square (интегральная) атака на 4 раунда | Восстановление ключа последнего раунда на нескольких Λ-наборах по 256 выбранных открытых текстов, за секунды | Работает на 4–6 раундах, полный AES (10–14 раундов) вне досягаемости. Плюс оценка Гровера для 128 и 256 бит | 3 |
| AES, «Кузнечик» | Дифференциальный и линейный анализ S-блоков | Таблицы DDT и LAT, дифференциальная равномерность (4 у AES, 8 у π), нелинейность (112 и 100) | По числу активных S-блоков оцениваем, сколько раундов хватает против дифференциальных и линейных атак | 3 |
| Режим CBC | Padding oracle (Водене) | Расшифровка без ключа, ≤ 256 запросов на байт | Применима к CBC без MAC; AEAD-режимы её исключают | 3 |
| Режим GCM | Повтор nonce (forbidden attack) | Восстановление ключа аутентификации H и подделка тега | Обоснование, почему nonce в конверте случайный и ключ каждый раз новый | 4 |

Атаки пишем в `analysis/attacks/`. Уязвимые варианты примитивов живут там же и никогда не регистрируются в основном реестре.

## Тестирование и правила разработки

Примитив считается готовым, только когда он побитово совпадает с официальными тест-векторами и проходит CI с санитайзерами. Совпадение с собственными тестами не доказывает ничего.

### Уровни тестов

1. **Модульные** (GoogleTest) — на каждую внутреннюю функцию:
   - NTT и обратное NTT дают тождество; умножение через NTT совпадает со школьным;
   - декодеры Рида–Соломона и Рида–Маллера исправляют t ошибок и отказывают при t + 1;
   - S-блок и обратный S-блок взаимно обратны.
2. **KAT** — векторы лежат в `tests/kat/`:
   - FIPS 202 и CAVP для SHA-3;
   - NIST ACVP для ML-KEM (keyGen, encapDecap);
   - векторы из официального пакета HQC той версии, которую реализуем, вместе с его DRBG для воспроизведения случайности;
   - FIPS 197 и CAVP для AES;
   - контрольные примеры из текстов ГОСТ 34.12-2015 и 34.13-2015;
   - SP 800-38A и GCM-векторы NIST.
3. **Дифференциальные** — случайные входы прогоняем через нашу реализацию и через liboqs или OpenSSL. Например, наш Encaps против чужого Decaps и наоборот.
4. **Свойства** — Decaps(Encaps) = K на 10⁴ случаев для каждого набора; повреждённый ct даёт другой K; open(seal) = pt для всех пар KEM × AEAD.
5. **Фаззинг** (libFuzzer) — парсеры конверта, файлов хранилища, Decaps на произвольных байтах.

### Стек и структура репозитория

- C++20, CMake ≥ 3.24, GCC 13+ и Clang 17+. Зависимости через `FetchContent`: GoogleTest, CLI11, nlohmann/json. liboqs и OpenSSL — только для целей `tests` и `pqbench`.
- Стиль: `clang-format` (на основе стиля Google) и `clang-tidy`, оба проверяются в CI. Предупреждения считаются ошибками (`-Wall -Wextra -Werror`).
- CI на GitHub Actions: сборка GCC и Clang, тесты под ASan и UBSan, проверка форматирования, быстрый смоук-прогон бенчмарков.
- Git: `main` защищён, работа идёт в ветках `feat/<модуль>`. В `main` — только через PR с ревью и зелёным CI.

## Риски и открытые вопросы

Самый вероятный срыв — HQC не совпадёт с KAT. Поэтому версию спецификации фиксируем до начала реализации.

| Риск | Что делаем |
| --- | --- |
| Спецификация HQC менялась в 2025 году, а стандарт NIST ещё в работе | Берём одну датированную версию вместе с её KAT и фиксируем в README. Для переходного сравнения держим liboqs |
| HQC не сходится с KAT из-за мелочей: порядок битов, доменные байты, сэмплер | Отлаживаем покомпонентно, сравнивая промежуточные значения с официальной референсной реализацией на C под отладчиком |
| Интерфейсы меняются на ходу и ломают чужую работу | После старта реализации меняем их только через PR с ревью всех четверых |
| Шумные измерения скорости на ноутбуках | Одна эталонная машина, процедура из пункта 3, медианы вместо средних |
| Атака через оракул или ISD оказывается сложнее, чем думали | Запасной вариант для обоих KEM — timing-демонстрация плюс аналитическая оценка стойкости с числами из спецификации |
